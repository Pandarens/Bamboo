# Bamboo — техническое задание

Диагностика и оптимизация Windows 11 без плацебо.

Версия документа: 0.1 · Статус: черновик · Лицензия проекта: GPLv3 (обусловлено Slint)

---

## 1. Цели и принципы

### 1.1 Что это

Bamboo — резидентная утилита для Windows 11, которая непрерывно наблюдает за системой, объясняет пользователю причины деградации производительности и предлагает обратимые действия по её устранению. Опционально — применяет часть действий автономно.

Ключевое отличие от существующих решений: Bamboo не набор твиков реестра, а система наблюдения с обратной связью. Каждое действие измеримо, журналируется и отменяется.

### 1.2 Принципы

**Обратимость.** Ни одно действие не выполняется без записи обратного рецепта в журнал. Кнопка полного отката доступна из любого экрана.

**Никакого плацебо.** Bamboo не реализует «очистку RAM», «дефрагментацию реестра», «ускорение интернета» и прочие функции без доказанного эффекта. Отказ от них документируется явно — это часть позиционирования.

**Успокаивать по умолчанию.** Индустрия оптимизаторов построена на генерации тревоги. Bamboo при отсутствии проблем говорит, что проблем нет. Предупреждения выдаются только при отклонении от базовой линии конкретной машины.

**Молчание — состояние по умолчанию.** Уведомление это дорогая валюта. Лимит — одно в сутки. Дважды отклонённое предложение больше не повторяется никогда.

**Нулевая телеметрия.** Ни одного исходящего сетевого запроса, кроме опциональной проверки обновлений. Все данные остаются на машине.

**Собственная скромность.** Bamboo обязан укладываться в свой ресурсный бюджет (раздел 4) и применяет EcoQoS к собственным процессам.

### 1.3 Антицели

Не входит в объём работ:

- Антивирусные функции любого рода
- Файрвол и блокировка сетевых соединений (только наблюдение и атрибуция)
- Модификация системных файлов, удаление компонентов Windows, отключение Defender или Windows Update как компонентов
- «Дебloating» — массовое удаление предустановленных приложений
- Разгон, вольтмод, управление вентиляторами
- Очистка диска от временных файлов (это делает встроенный Storage Sense)
- Расчёт write amplification factor — потребительские NVMe не отдают данные для его вычисления

### 1.4 Целевая платформа

- Windows 11 21H2 и новее (x64, ARM64)
- Windows 10 22H2 — деградированный режим: недоступны EcoQoS-специфичные API 22H2+, часть визуальных эффектов окна
- Минимальная поддерживаемая конфигурация: 4 ГБ RAM, 2 ядра

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Агент | Процесс в пользовательской сессии: трей, виджет, уведомления |
| Брокер | Служба Windows под SYSTEM, выполняющая привилегированные операции |
| Действие | Атомарное изменение состояния системы с известным обратным рецептом |
| Журнал | Транзакционный лог применённых действий |

| Сторожевой таймер | Механизм автоотката при деградации после действия |
| Видеорегистратор | Кольцевой буфер ETW-событий, сбрасываемый на диск при срабатывании триггера |

## 3. Архитектура

### 3.1 Компоненты

```
┌─────────────────────────────────────────────────────┐
│ bamboo-agent.exe    (пользовательская сессия, без прав администратора) │
│   трей · виджет (Slint) · главное окно · тосты      │
└──────────────────────┬──────────────────────────────┘
                       │ named pipe \\.\pipe\bamboo-{sid}
                       │ bincode, длина-префикс
┌──────────────────────┴──────────────────────────────┐
│ bamboo-service.exe  (SYSTEM, автозапуск с задержкой) │
│                                                       │
│  collect ──▶ analyze ──▶ policy ──▶ actuate          │
│     │           │           │           │            │
│     └──▶ store ◀┘           └──▶ journal ◀┘          │
│                                                       │
│  etw (сессия реального времени)                      │
└──────────────────────┬──────────────────────────────┘
                       │ Win32 / NT API / IOCTL
                  ┌────┴────┐
                  │ Windows │
                  └─────────┘
```

### 3.2 Разделение привилегий

Агент работает без повышения прав. Все операции, требующие прав администратора, выполняет брокер. Это исключает необходимость UAC при каждом запуске UI и ограничивает поверхность атаки одним процессом с чётко определённым протоколом.

Брокер не доверяет агенту. Каждая команда проходит валидацию:

1. Проверка, что клиент канала — процесс с тем же образом (сравнение по подписи или, для неподписанных сборок, по SHA-256 файла образа и полному пути)
2. Проверка SID клиента — команда применима только к процессам того же пользователя, кроме явно системных операций
3. Проверка команды против белых списков (раздел 11.3)
4. Проверка уровня риска против текущих настроек автономности

### 3.3 Дескриптор безопасности канала

Канал создаётся брокером с явным SD: разрешён доступ только `BUILTIN\Administrators` и интерактивным пользователям текущей сессии. Запрещён доступ `Everyone`, `ANONYMOUS LOGON`, `NETWORK`. Флаг `PIPE_REJECT_REMOTE_CLIENTS` обязателен.

Отсутствие этой проверки превращает Bamboo в локальную уязвимость повышения привилегий — любой процесс сможет попросить SYSTEM-службу выполнить действие.

### 3.4 Структура воркспейса

```
crates/
  bamboo-core       типы, ошибки, единицы измерения. Без зависимостей от Windows
  bamboo-sys        весь unsafe. Обёртки над Win32/NT/IOCTL
  bamboo-collect    семплирование, кольцевые буферы, дельты
  bamboo-etw        сессии трейсинга, парсинг событий
  bamboo-store      агрегация, персистентность, SQLite
  bamboo-analyze    чистые функции над временными рядами
  bamboo-policy     скоринг, белые списки, уровни риска
  bamboo-actuate    исполнение действий и обратных рецептов
  bamboo-journal    транзакционный лог, сторожевой таймер
  bamboo-ipc        протокол, сериализация, клиент и сервер
  bamboo-service    брокер
  bamboo-agent      трей, виджет, главное окно, уведомления
  bamboo-cli        отладочная утилита, дамп трасс, воспроизведение
tools/
  trace-replay      прогон анализаторов на записанных трассах
fixtures/
  traces/           эталонные трассы для тестов
```

Два инвариантных правила:

**Весь `unsafe` — только в `bamboo-sys`.** В остальных крейтах `#![forbid(unsafe_code)]` на уровне модуля. Это делает аудит выполнимым.

**`bamboo-analyze` не знает о Windows.** На вход — временные ряды и метаданные, на выход — наблюдения. Позволяет тестировать логику детекции на записанных трассах без живой системы.

## 4. Ресурсный бюджет

Жёсткие лимиты. Нарушение любого — блокирующий баг, а не оптимизация «на потом».

| Метрика | Брокер | Агент (виджет скрыт) | Агент (виджет открыт) |
|---|---|---|---|
| Рабочий набор | ≤ 15 МБ | ≤ 12 МБ | ≤ 30 МБ |
| Приватные байты | ≤ 12 МБ | ≤ 10 МБ | ≤ 25 МБ |
| CPU, среднее за час | ≤ 0.1% | ≤ 0.02% | ≤ 0.5% |
| Wakeups в минуту | ≤ 20 | ≤ 5 | по частоте кадров |
| Запись на диск в сутки | ≤ 20 МБ | 0 | 0 |
| Размер на диске (данные) | ≤ 200 МБ | — | — |

Измерение — автоматическое, в CI на выделенной машине, суточный прогон перед каждым релизом. Отчёт публикуется в репозитории.

### 4.1 Приёмы для соблюдения бюджета

- Slint с фичей `renderer-software`, переменная `SLINT_BACKEND=winit-software`. GPU-контекст не создаётся вообще
- Переиспользование буфера `NtQuerySystemInformation` — реаллокация только по `STATUS_INFO_LENGTH_MISMATCH`
- `CreateWaitableTimerEx` с флагом `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` выключен, вместо него большой `TolerableDelay` для timer coalescing
- Адаптивная частота опроса (раздел 6.2)
- Отсутствие async-рантайма. Обычные потоки: коллектор, ETW, IPC, аналитика
- `SetProcessInformation` с `ProcessPowerThrottling` (`PROCESS_POWER_THROTTLING_EXECUTION_SPEED`) на собственные процессы
- `SetProcessInformation` с `ProcessMemoryPriority` = 3 на брокер
- Однократный `SetProcessWorkingSetSizeEx(-1, -1)` после инициализации, больше никогда
- При скрытии виджета — `DestroyWindow`, а не `ShowWindow(SW_HIDE)`. Отписка от потока данных

## 5. Модуль bamboo-sys

Типизированные безопасные обёртки над системными API. Ниже — перечень требуемой функциональности с указанием используемых вызовов.

### 5.1 Снимок процессов

`NtQuerySystemInformation(SystemProcessInformation)` — единственный источник для базового опроса. Возвращает связный список `SYSTEM_PROCESS_INFORMATION` с массивом `SYSTEM_THREAD_INFORMATION` для каждого процесса.

Извлекаемые поля: PID, PPID, имя образа, `CreateTime`, `UserTime`, `KernelTime`, `WorkingSetPrivateSize`, `PrivatePageCount`, `VirtualSize`, `HandleCount`, `NumberOfThreads`, `ReadOperationCount`, `WriteOperationCount`, `ReadTransferCount`, `WriteTransferCount`, `OtherTransferCount`, `SessionId`, `BasePriority`.

Стоимость: 1–3 мс на 300 процессов, буфер 300–500 КБ.

**Запрещено:** цикл `OpenProcess` + `GetProcessMemoryInfo` по каждому PID. Это сотни системных вызовов и открытие дескрипторов на чужие процессы, что триггерит поведенческие детекторы EDR.

### 5.2 Процессорное время системы и DPC

`NtQuerySystemInformation(SystemProcessorPerformanceInformation)` — на ядро: `IdleTime`, `KernelTime`, `UserTime`, `DpcTime`, `InterruptTime`, `InterruptCount`.

`NtQuerySystemInformation(SystemInterruptInformation)` — детализация прерываний.

Назначение: если система нагружена, а сумма по процессам мала — виновник на уровне драйверов. Это диагноз, который не может поставить ни один процессный монитор.

### 5.3 Расширенная информация о процессе

По требованию (не в цикле опроса):

- `QueryFullProcessImageNameW` — полный путь образа
- Командная строка: `NtQueryInformationProcess(ProcessCommandLineInformation)` (Win8.1+), фолбэк на чтение PEB
- `GetProcessInformation(ProcessPowerThrottling)` — текущее состояние QoS
- `GetProcessInformation(ProcessMemoryPriority)` — текущий приоритет памяти
- `GetGuiResources(GR_GDIOBJECTS / GR_USEROBJECTS)` — счётчики GDI и User объектов
- `GetProcessIoCounters` — при необходимости точечно
- Проверка подписи: `WinVerifyTrust` + `CryptQueryObject` для издателя

### 5.4 Управление процессами

| Операция | API |
|---|---|
| EcoQoS вкл/выкл | `SetProcessInformation` + `PROCESS_POWER_THROTTLING_STATE` с `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` |
| Приоритет памяти | `SetProcessInformation` + `MEMORY_PRIORITY_INFORMATION` (1..5) |
| Заморозка | Job object + `SetInformationJobObject(JobObjectFreezeInformation)` с `Freeze = TRUE` |
| Разморозка | То же с `Freeze = FALSE` |
| Приоритет | `SetPriorityClass` |
| Дамп | `MiniDumpWriteDump` с `MiniDumpWithFullMemory` |

**Заморозка через Job object, а не `NtSuspendProcess`.** `JobObjectFreezeInformation` (Windows 10 1709+) — документированный механизм, которым Windows усыпляет UWP-приложения. Он корректно обрабатывает создание новых потоков в замороженном процессе и не оставляет процесс в состоянии, из которого невозможно выйти при падении Bamboo.

Требование: job object должен создаваться с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE = false` и храниться дескриптор в брокере. При остановке службы все job-объекты размораживаются в обработчике `SERVICE_CONTROL_STOP` до закрытия дескрипторов.

### 5.5 Службы

`OpenSCManagerW`, `EnumServicesStatusExW`, `QueryServiceConfigW`, `QueryServiceConfig2W` (для описания, отложенного автозапуска, действий при сбое), `ChangeServiceConfigW`, `ControlService`, `StartServiceW`.

Обязательное чтение: триггеры запуска через `QueryServiceConfig2W(SERVICE_CONFIG_TRIGGER_INFO)`. Служба с триггерным запуском в простое не потребляет ресурсов, её отключение бессмысленно и вредно. Bamboo обязан показывать это явно.

### 5.6 Автозагрузка и задачи планировщика

Автозагрузка: реестр `HKLM|HKCU\Software\Microsoft\Windows\CurrentVersion\Run` и `RunOnce`, папки Startup, `HKLM\...\Explorer\StartupApproved` для состояния включения.

Планировщик: COM-интерфейс `ITaskService` / `ITaskFolder` / `IRegisteredTask`. Требуется чтение триггеров, действий, состояния последнего запуска, кода возврата.

### 5.7 SMART и здоровье накопителей

**NVMe:** `DeviceIoControl` с `IOCTL_STORAGE_QUERY_PROPERTY`, `STORAGE_PROPERTY_QUERY.PropertyId = StorageDeviceProtocolSpecificProperty`, `STORAGE_PROTOCOL_SPECIFIC_DATA` с `ProtocolType = ProtocolTypeNvme`, `DataType = NVMeDataTypeLogPage`, `ProtocolDataRequestValue = 0x02` (SMART / Health Information Log).

Извлекаемые поля структуры `NVME_HEALTH_INFO_LOG`:

| Поле | Смысл | Использование |
|---|---|---|
| `DataUnitWritten` | 128 бит, единицы по 512 000 байт | Накопленный объём хост-записей |
| `DataUnitRead` | То же для чтения | Соотношение чтение/запись |
| `PercentageUsed` | Оценка контроллера, может превышать 100 | Основной индикатор износа |
| `AvailableSpare` | Процент резервных блоков | Тревога при падении |
| `AvailableSpareThreshold` | Порог производителя | Сравнение с предыдущим |
| `MediaErrors` | 128 бит, ошибки целостности | Рост — критический сигнал |
| `Temperature` | Кельвины, смещение 273 | Детект троттлинга |
| `CriticalWarning` | Битовая маска | Прямое предупреждение контроллера |
| `PowerCycle`, `PowerOnHours` | Счётчики | Контекст для проекций |
| `UnsafeShutdowns` | Некорректные выключения | Диагностика питания |

**SATA:** `IOCTL_ATA_PASS_THROUGH` с командой SMART READ DATA (0xB0 / 0xD0). Атрибут 241 — Total LBAs Written. Показатель остаточного ресурса вендор-специфичен: 177 (Samsung, Wear Leveling Count), 231 (Intel/Crucial, SSD Life Left), 202, 233. Требуется таблица соответствий по производителю из `StorageDeviceProperty.VendorId` и `ProductId`.

При невозможности прочитать SMART (RAID-контроллер, USB-мост без поддержки трансляции) — явное сообщение о невозможности, не оценка.

### 5.8 Питание и пробуждения

- `CallNtPowerInformation(SystemPowerRequestList)` — процессы, удерживающие систему от сна через `SetThreadExecutionState`. Основа для определения «идёт воспроизведение или загрузка»
- `CallNtPowerInformation(SystemBatteryState)` — состояние батареи
- `GetSystemPowerStatus` — питание от сети или батареи
- `PowerRegisterSuspendResumeNotification` — события сна и пробуждения
- Журнал `Microsoft-Windows-Kernel-Power`, событие 107 (возобновление) и 42 (переход в сон) — причина пробуждения
- `powercfg /lastwake` даёт то же самое, но требует парсинга вывода; предпочтителен прямой доступ к журналу через `EvtQuery`

### 5.9 Состояние пользователя

- `GetLastInputInfo` — время с последнего ввода
- `SHQueryUserNotificationState` — `QUNS_RUNNING_D3D_FULL_SCREEN`, `QUNS_PRESENTATION_MODE`, `QUNS_BUSY`, `QUNS_QUIET_TIME`, `QUNS_ACCEPTS_NOTIFICATIONS`
- `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` — смена активного окна. Событийно, не поллингом
- `WTSRegisterSessionNotification` — блокировка и разблокировка сессии
- `GetForegroundWindow` + `GetWindowThreadProcessId` — привязка окна к процессу

### 5.10 Сеть

`GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL)` и `GetExtendedUdpTable` — связка соединение → PID. Стоимость низкая, вызывается раз в 30 секунд.

Назначение: атрибуция фоновой сетевой активности и проверка перед заморозкой (наличие активных соединений — стоп-сигнал).

## 6. Сбор данных

### 6.1 Метрики на процесс

Собираются каждый тик:

| Метрика | Источник | Тип |
|---|---|---|
| CPU, наносекунды | `UserTime` + `KernelTime`, дельта | накопительный |
| Рабочий набор | `WorkingSetPrivateSize` | мгновенный |
| Приватные страницы | `PrivatePageCount` | мгновенный |
| Виртуальный размер | `VirtualSize` | мгновенный |
| Дескрипторы | `HandleCount` | мгновенный |
| Потоки | `NumberOfThreads` | мгновенный |
| Чтение, байт | `ReadTransferCount`, дельта | накопительный |
| Запись, байт | `WriteTransferCount`, дельта | накопительный |
| Прочий I/O, байт | `OtherTransferCount`, дельта | накопительный |
| Операций чтения | `ReadOperationCount`, дельта | накопительный |
| Операций записи | `WriteOperationCount`, дельта | накопительный |

Реже (раз в минуту): GDI-объекты, User-объекты — через `GetGuiResources`, только для процессов с окнами.

### 6.2 Частота опроса

| Условие | Интервал |
|---|---|
| Виджет открыт | 1 с |
| Виджет скрыт, питание от сети, пользователь активен | 5 с |
| Пользователь неактивен > 5 мин | 15 с |
| Питание от батареи | 15 с |
| Батарея < 20% | 60 с |
| Полноэкранное приложение / игра | 30 с, тяжёлые анализаторы выключены |

Переключение частоты — с гистерезисом, чтобы не осциллировать на границе.

### 6.3 Ограничения счётчиков ввода-вывода

Обязательно документировать в UI. `IO_COUNTERS` отражает **логический** ввод-вывод:

- Попадания в кэш файловой системы считаются как I/O, хотя обращения к диску не было
- Отложенная запись модифицированных страниц выполняется системным потоком, поэтому реальный сброс на диск приписывается процессу `System`. Приложения, интенсивно работающие с memory-mapped файлами (СУБД, Docker, движки виртуализации), в этих счётчиках систематически недооценены
- Сетевой файловый ввод-вывод и работа с пайпами попадают в те же счётчики

Следствие: `IO_COUNTERS` используется для дешёвого постоянного рейтинга. Точная атрибуция физических записей — только через ETW (раздел 7).

### 6.4 Метрики системы

Каждый тик: свободная/используемая физическая память, commit charge и лимит, кэш; на ядро — idle/kernel/user/DPC/interrupt.

Раз в 30 с: таблица TCP/UDP с привязкой к PID.

Раз в час: SMART всех накопителей.

При событии: смена активного окна, блокировка/разблокировка, сон/пробуждение, подключение/отключение питания.

## 7. ETW

### 7.1 Постоянная сессия

Провайдер `Microsoft-Windows-Kernel-Process`, ключевое слово `WINEVENT_KEYWORD_PROCESS`. События: `ProcessStart` (1), `ProcessStop` (2).

Объём: десятки событий в минуту на типичной системе. Стоимость пренебрежима.

Назначение — решение фундаментальной проблемы: **опрос раз в 5 секунд не видит процессы, живущие 2 секунды**. Именно короткоживущие процессы (`CompatTelRunner`, `MoUsoCoreWorker`, `TiWorker`, сканы Defender, задачи планировщика) вызывают внезапные фризы. Пользователь открывает диспетчер задач — там уже пусто.

Каждый процесс фиксируется с PID, PPID, командной строкой, временем жизни, потреблённым CPU-временем, даже если прожил 200 мс.

### 7.2 Атрибуция происхождения

По цепочке родителей восстанавливается источник:

- Родитель `svchost.exe -k netsvcs` с загруженным `schedsvc.dll` → задача планировщика. Точное имя задачи — через провайдер `Microsoft-Windows-TaskScheduler` (события 100, 102, 200, 201) или сопоставление по времени с COM-запросом к планировщику
- Родитель `services.exe` → служба
- Родитель `explorer.exe` → запуск пользователем
- Родитель `MsMpEng.exe` → активность Defender
- Родитель `TrustedInstaller.exe` → обслуживание компонентов

Требование к отчёту: вместо «неизвестный процесс нагружал CPU» — «задача `\Microsoft\Windows\Application Experience\Microsoft Compatibility Appraiser` заняла 4 минуты одного ядра в 03:14».

### 7.3 Сессия расследования

Включается только по триггеру или явному запросу, на 60–120 секунд.

Провайдеры:
- `Microsoft-Windows-Kernel-Disk` — физические операции с диска, с указанием устройства, смещения, размера, длительности
- `Microsoft-Windows-Kernel-File` — пути файлов, операции создания/записи/удаления
- `Microsoft-Windows-Kernel-Network` — сетевой ввод-вывод с атрибуцией
- `Microsoft-Windows-Kernel-Power` — переходы состояний, wakeups

**Категорически не включать постоянно:** `CSWITCH` (переключения контекста) и `PROFILE` (семплирование стеков). Первый генерирует десятки тысяч событий в секунду и сам съест 3–5% CPU. Допустим только внутри явно запрошенной пользователем сессии профилирования с индикатором в UI.

### 7.4 Видеорегистратор

Кольцевой буфер ETW-событий в памяти на последние 5–10 минут, объём 4–8 МБ. Пишется постоянно, никуда не сохраняется.

При срабатывании триггера буфер целиком сбрасывается на диск:

- CPU > 25% суммарно при простое пользователя > 3 мин
- Запись на диск > 100 МБ за 60 с при простое
- Один процесс > 50% одного ядра дольше 30 с без фокуса
- Явное нажатие «зафиксировать» в UI

Результат: ретроспектива за минуты **до** события. Обычные мониторы этого не дают — пока пользователь откроет окно, всплеск закончился.

Хранится последние 10 срабатываний, старые ротируются.

### 7.5 Реализация

Крейт: `ferrisetw` либо собственная обёртка над `StartTraceW` / `EnableTraceEx2` / `ProcessTrace`. Собственная обёртка предпочтительна для контроля над размером буферов и режимом реального времени.

Обязательно: `EVENT_TRACE_PROPERTIES` с `LogFileMode = EVENT_TRACE_REAL_TIME_MODE`, размер буфера 64 КБ, минимум 4 буфера, `FlushTimer = 1`. Корректная остановка сессии в обработчике завершения службы — «висящие» ETW-сессии переживают процесс и накапливаются.

## 8. Хранилище

### 8.1 Проблема объёма

300 процессов × 1 сэмпл / 5 с = 5,2 млн записей в сутки. Строка на процесс на сэмпл в SQLite недопустима.

### 8.2 Схема даунсемплинга

| Уровень | Разрешение | Глубина | Хранение |
|---|---|---|---|
| L0 | 1 с | 10 мин | Кольцевой буфер в памяти |
| L1 | 1 мин | 24 ч | Кольцевой буфер в памяти |
| L2 | 15 мин | 30 сут | SQLite |
| L3 | 1 ч | 12 мес | SQLite, только агрегаты по процессу |

Агрегация при переходе между уровнями: для накопительных метрик — сумма, для мгновенных — среднее, максимум и минимум (три значения, чтобы не потерять всплески при усреднении).

Объём в памяти: L0 + L1 ≈ 4–6 МБ при 300 процессах. Укладывается в бюджет.

Сброс L2 на диск — раз в час, батчем, в одной транзакции. Это даёт целевые ≤ 20 МБ записи в сутки.

### 8.3 Идентификация процессов

PID переиспользуются. Ключ временного ряда — не PID, а стабильный идентификатор приложения:

```
app_key = normalize(image_path) + ":" + publisher_or_hash
```

`normalize` приводит путь к нижнему регистру и разворачивает переменные окружения. Для приложений с версионированными путями (`Discord\app-1.0.9034\`) применяется правило схлопывания версии в токен.

Экземпляр процесса идентифицируется парой `(pid, create_time)` — эта комбинация уникальна.

### 8.4 SQLite

Режим WAL, `synchronous = NORMAL`, `journal_size_limit` ограничен. Крейт `rusqlite` с фичей `bundled`.

Таблицы: `apps`, `samples_l2`, `samples_l3`, `observations`, `journal`, `smart_history`, `boot_history`, `wake_events`, `system_diff`, `user_prefs`.

Отдельный файл для журнала действий (раздел 12) — он должен переживать повреждение основной базы.

### 8.5 Экспорт трасс

Коллектор умеет писать сырой поток сэмплов в файл (`bamboo-cli record`). Формат — длина-префикс + bincode, сжатие zstd.

Назначение двойное: тесты анализаторов на реальных данных в CI и возможность пользователю приложить трассу к issue, чтобы разработчик воспроизвёл проблему без доступа к машине.

## 9. Анализаторы

Все анализаторы — чистые функции в `bamboo-analyze`. Вход: временные ряды и метаданные. Выход: `Observation` со степенью уверенности 0..1.

### 9.1 Рост памяти

Скользящее окно 4 часа по метрике `PrivatePageCount`. Линейная регрессия методом наименьших квадратов.

Критерии наблюдения:
- Наклон > 20 МБ/час
- R² > 0.9
- Отсутствие сброса: минимум последнего часа выше максимума первого часа окна
- Процесс жив дольше 6 часов

Отдельно и с более высоким приоритетом — рост `HandleCount` (> 100/час при R² > 0.85) и GDI/User-объектов (> 50/час). Это классические утечки, чётко видимые снаружи и почти всегда настоящие.

**Формулировка вывода.** Снаружи, без инструментирования процесса, детектируется не утечка, а монотонный рост. Текст обязан это отражать: «похоже на утечку памяти» с предложением снять дамп через `MiniDumpWriteDump` — готовый артефакт для разработчика приложения. Не «обнаружена утечка».

### 9.2 Фоновые всплески CPU

Срабатывание: процесс потребляет > 20% одного ядра дольше 20 с при одновременном выполнении условий:
- `GetLastInputInfo` показывает простой > 3 мин
- Активное окно не менялось в течение всплеска
- `SystemPowerRequestList` не содержит запросов `ES_DISPLAY_REQUIRED` (иначе идёт воспроизведение)
- `SHQueryUserNotificationState` не в состоянии `QUNS_RUNNING_D3D_FULL_SCREEN` или `QUNS_BUSY`

Обогащение: атрибуция происхождения (7.2), совокупное время за неделю, сравнение с базовой линией.

### 9.3 Нагрузка уровня драйверов

Условие: суммарная загрузка CPU > 15%, при этом сумма по всем процессам < 60% от неё, а `DpcTime + InterruptTime` составляет > 10% от общего времени.

Вывод: указание, что проблема на уровне драйверов, а не приложений. Определение конкретного драйвера требует `xperf` и выходит за рамки; Bamboo указывает направление и рекомендует проверить драйверы сетевого адаптера, звука и накопителей как наиболее частые источники.

Ценность высока: пользователи месяцами ищут «вирус», когда причина — драйвер, и ни один процессный монитор этого не показывает.

### 9.4 Расход ресурса SSD

Ежечасное чтение SMART. Дельта `DataUnitWritten` между чтениями даёт скорость записи.

Проекция:
```
суточные_записи = среднее за 7 дней
остаток_TBW = TBW_паспорт − накопленные_записи
лет_до_исчерпания = остаток_TBW / (суточные_записи × 365)
```

`TBW_паспорт` — из локальной таблицы моделей; при отсутствии модели используется консервативная оценка 300 ТБ на терабайт ёмкости с явной пометкой «оценка».

**Поведение по умолчанию — успокаивать.** У типичного пользователя выходит 10–20 ГБ в сутки при ресурсе 600 ТБ, то есть около сотни лет. Честный вывод в подавляющем большинстве случаев: «с накопителем всё в порядке, израсходовано 2% ресурса».

Предупреждение выдаётся только при:
- Записи > 200 ГБ/сутки в среднем за неделю (аномалия почти всегда)
- Росте `MediaErrors` относительно предыдущего чтения
- `AvailableSpare` ниже `AvailableSpareThreshold`
- Ненулевом `CriticalWarning`
- Проекции исчерпания менее 3 лет
- Отклонении от собственной базовой линии машины более чем втрое

При срабатывании — атрибуция: топ процессов по записи за период. Типичные настоящие виновники: неправильно настроенные кэши Electron-приложений, разросшийся `.vhdx` Docker Desktop, свопинг из-за нехватки RAM, индексатор Windows Search, циклически переустанавливающееся обновление через `TiWorker`.

### 9.5 Простаивающие приложения

Композитный признак. Время работы само по себе **не является** сигналом — Postgres может висеть месяцами, и это нормально.

Четыре измерения, все должны сойтись:

**Время с последнего взаимодействия** — не время запуска. По хуку `EVENT_SYSTEM_FOREGROUND`: когда окно процесса последний раз было активным. Для процессов без окон критерий не применяется, они анализируются отдельно.

**Стоимость простоя** — CPU-время, записи на диск и wakeups за период бездействия. Приложение, честно спящее на нуле, не трогается независимо от времени работы. Это условие отсекает большинство ложных срабатываний.

**Тренд памяти** — растёт ли рабочий набор без взаимодействия.

**Отсутствие незавершённой работы** — стоп-сигналы: активные TCP-соединения, открытые дескрипторы на пользовательские файлы вне временных папок, живые дочерние процессы, регистрация в `SystemPowerRequestList`.

Формулировка вывода — конкретная и измеримая: не «программа давно запущена», а «Slack не использовался 3 дня, вырос до 2.1 ГБ, разбудил процессор 40 000 раз за ночь».

### 9.6 Анализ пробуждений

Источник: журнал `Microsoft-Windows-Kernel-Power`, событие 107; `powercfg /lastwake` как перекрёстная проверка.

Классификация причины: Wake Timer (с указанием задачи планировщика), сетевой адаптер (Wake-on-LAN / Wake on Magic Packet), устройство HID, кнопка питания, крышка, RTC.

Для ноутбуков это прямой ответ на вопрос «почему рюкзак был горячим». Данные доступны без дополнительной инструментации.

Действие: отключение Wake Timer у конкретной задачи, отключение `Allow this device to wake the computer` у адаптера — обратимые операции.

### 9.7 Разряд в Modern Standby

`powercfg /sleepstudy` формирует HTML-отчёт с разбивкой по сессиям сна: доля времени в глубоких состояниях, топ активаторов, потребление на процент батареи.

Bamboo парсит отчёт (или, предпочтительнее, читает те же данные из провайдера `Microsoft-Windows-Kernel-Power` и `SleepStudy` ETL) и показывает: какой процесс не давал уйти в глубокие состояния, сколько батареи это стоило.

### 9.8 Регрессии загрузки

Журнал `Microsoft-Windows-Diagnostics-Performance/Operational`:
- Событие 100 — общее время загрузки, `BootTime`, `MainPathBootTime`, `BootPostBootTime`
- Событие 200 — деградация загрузки с указанием компонента и времени в миллисекундах
- События 101–110 — конкретные тормозящие приложения, службы, драйверы

Windows собирает это самостоятельно и не показывает пользователю.

Bamboo строит график за доступный период (обычно несколько месяцев) и коррелирует изменения с системным диффом (9.9): «время загрузки выросло на 8 секунд после установки X 12 марта».

### 9.9 Системный дифф

Еженедельный снимок: службы, задачи планировщика, элементы автозагрузки, драйверы (`EnumDeviceDrivers` + версии), установленные приложения (реестр Uninstall + пакеты Appx).

Дифф с предыдущим снимком. Софт часто устанавливает фоновые обновляторы молча — сам факт «за неделю добавилось три задачи планировщика» уже полезен без каких-либо действий.

### 9.10 Сетевая атрибуция

Раз в 30 с — снимок TCP/UDP с PID. Агрегация: какие процессы, куда, как часто.

Только наблюдение. Блокировка соединений не входит в объём (это функция файрвола).

## 10. Базовая линия и период обучения

### 10.1 Период обучения

Первые 14 суток после установки Bamboo только наблюдает. Действия недоступны в автономном режиме; ручные действия доступны с явным предупреждением, что базовая линия ещё не сформирована.

В UI — прогресс-индикатор: «изучаю систему, осталось 9 дней».

### 10.2 Содержание базовой линии

Для каждого приложения: типичное потребление CPU, памяти, записи; типичное время работы; частота взаимодействия; доля времени с фокусом; типичный профиль по часам суток и дням недели.

Для системы: типичное время загрузки, типичный суточный объём записи, типичное число пробуждений за ночь.

Хранение: устойчивые статистики (медиана, межквартильный размах), не среднее и не стандартное отклонение — распределения здесь сильно скошенные, среднее уводит порог.

### 10.3 Использование

Аномалия определяется как отклонение от собственной базовой линии, а не от абсолютных порогов. Абсолютные пороги (раздел 9) — только для случаев, где физика однозначна (рост `MediaErrors`, `AvailableSpare` ниже порога).

Базовая линия пересчитывается скользящим окном 30 суток, с исключением периодов, когда действовали изменения Bamboo (иначе система обучится на собственном эффекте).

## 11. Политики и действия

### 11.1 Иерархия действий по риску

| Уровень | Действие | Обратимость | Автономно |
|---|---|---|---|
| 1 | EcoQoS (`ProcessPowerThrottling`) | Мгновенная, полная | Да |
| 1 | Понижение приоритета памяти | Мгновенная, полная | Да |
| 2 | Отложенный автозапуск службы | Полная | Да |
| 2 | Отключение элемента автозагрузки | Полная | С подтверждением |
| 3 | Отключение Wake Timer задачи | Полная | С подтверждением |
| 3 | Отключение задачи планировщика | Полная | С подтверждением |
| 4 | Заморозка процесса (Job freeze) | Полная, но с рисками | Только вручную |
| 5 | Остановка службы | Полная | Только вручную |
| 6 | Отключение службы (`SERVICE_DISABLED`) | Полная | Только вручную |

Автономный режим имеет право на уровни 1–2. Уровни 3 и выше требуют явного подтверждения пользователя всегда.

### 11.2 Риски заморозки

Заморозка — единственное действие, способное вызвать каскадный отказ. Обязательные проверки перед применением:

**Взаимоблокировки.** Замороженный процесс продолжает удерживать мьютексы, критические секции и именованные объекты синхронизации. Если он держал разделяемый ресурс, зависнут его потребители. Проверка: наличие именованных объектов синхронизации, разделяемых с другими процессами; наличие зарегистрированных COM-серверов с активными клиентами. При обнаружении — отказ.

**Сетевые соединения.** Заморозка приводит к разрыву по таймауту и пробуждению приложения в неконсистентном состоянии. Проверка через `GetExtendedTcpTable` — наличие соединений в состоянии `ESTABLISHED` — отказ.

**Открытые файлы.** Дескрипторы на пользовательские файлы вне временных папок — отказ (риск потери данных).

**Античиты.** EAC, BattlEye, Vanguard, nProtect интерпретируют внешнее вмешательство в процесс как читерство, вплоть до блокировки аккаунта. Игры и античит-модули — в жёстком чёрном списке.

**Безопасность.** Заморозка антивируса, EDR, VPN-клиента, средств шифрования — запрещена абсолютно.

Заморозка сопровождается понижением приоритета памяти, чтобы страницы вытеснялись естественным путём. `EmptyWorkingSet` не применяется (раздел 11.5).

### 11.3 Белые списки

**Неизменяемый список** (не редактируется пользователем, не отображается как кандидат):

Ядро системы: `System`, `Registry`, `smss.exe`, `csrss.exe`, `wininit.exe`, `winlogon.exe`, `services.exe`, `lsass.exe`, `svchost.exe` (проверяется по параметру `-k`), `fontdrvhost.exe`, `dwm.exe`, `sihost.exe`, `ctfmon.exe`, `explorer.exe`, `RuntimeBroker.exe`, `ShellExperienceHost.exe`.

Безопасность: `MsMpEng.exe`, `NisSrv.exe`, `SecurityHealthService.exe`, все процессы с загруженным `elam`-драйвером, все процессы поставщиков антивирусов и EDR (по подписи), процессы с включённым Protected Process Light.

Инфраструктура: аудиостек (`audiodg.exe`, `AudioEndpointBuilder`), сетевой стек, драйверные службы GPU (`NVDisplay.ContainerLocalSystem`, `AMD External Events`, `igfxCUIService`), Windows Update при активной установке, `TrustedInstaller.exe` при активной операции.

Любой процесс в сессии 0 с интегрити-уровнем System.

**Пользовательский список.** Пополняется явно, а также автоматически: приложение, предложение по которому пользователь отклонил дважды, добавляется навсегда и молча.

**Список по классу.** Пользователь может исключить категорию целиком: игры, средства разработки, средства виртуализации, СУБД.

### 11.4 Профили

Профиль — именованный набор политик. Переключается вручную или по правилу.

| Профиль | Поведение |
|---|---|
| Обычный | Уровни 1–2 автономно, наблюдение полное |
| Игра | Все действия приостановлены, виджет скрыт, ETW-расследования выключены, частота опроса 30 с |
| Батарея | Агрессивный EcoQoS для фоновых приложений, опрос 15–60 с |
| Презентация | Полное молчание, никаких уведомлений |
| Работа | Исключены средства разработки и СУБД, остальное по обычным правилам |

Правила автопереключения: запуск полноэкранного D3D-приложения → Игра; отключение питания → Батарея; `QUNS_PRESENTATION_MODE` → Презентация.

### 11.5 Явно нереализуемые функции

Документируются в README с объяснением причины.

**«Очистка RAM»** через `EmptyWorkingSet` / `SetProcessWorkingSetSize(-1,-1)`. Не освобождает память, а вытесняет рабочий набор в файл подкачки. Приложение считывает всё обратно в течение секунд, результат — дисковый ввод-вывод, подтормаживания и лишняя запись на SSD. Все «RAM booster'ы» делают именно это.

**Массовое отключение служб.** В Windows 11 значительная часть служб запускается по триггерам и в простое не потребляет ресурсов. Отключение даёт нулевой выигрыш и ломает Wi-Fi, печать, Store через недели, когда пользователь уже забыл о своих действиях.

**Дефрагментация реестра, «ускорение интернета», «оптимизация игр».** Отсутствуют доказательства эффекта.

**Расчёт write amplification.** Потребительские NVMe не публикуют реальный объём записей в NAND, только хост-записи. Вычислить WAF невозможно; инструменты, показывающие эту цифру, её выдумывают.

## 12. Журнал и откат

### 12.1 Формат записи

```
{
  id, timestamp, actor: manual|auto, profile,
  target: { app_key, pid?, service_name?, task_path? },
  action: { kind, params },
  undo: { kind, params },
  prior_state: { ... },
  observation_id?,
  watchdog: { deadline, baseline_metrics },
  status: applied|reverted|expired|failed
}
```

`prior_state` содержит полное состояние до изменения, достаточное для восстановления даже если `undo` не сработает штатно.

### 12.2 Требования

Журнал ведётся в отдельном файле от основной базы. Запись — до применения действия, обновление статуса — после. При падении между этими моментами следующий запуск обнаружит запись без подтверждения и проверит фактическое состояние.

Перед любым действием уровня 5–6 создаётся точка восстановления системы (`SRSetRestorePoint`), если она не создавалась за последние 24 часа.

При остановке службы все job-объекты размораживаются, EcoQoS остаётся (он безвреден и переживает перезагрузку только пока процесс жив).

### 12.3 Откат

Три уровня:
- Отменить конкретное действие
- Отменить все действия за период (день, неделя, всё время)
- Полный сброс: откат всего журнала, очистка базовой линии, возврат в состояние сразу после установки

Кнопка полного отката присутствует на виджете постоянно и оформлена как деструктивное действие. Психологически это снимает страх экспериментировать с остальным.

### 12.4 Сторожевой таймер

После применения действия открывается окно наблюдения 48 часов. Фиксируется базовая линия метрик на момент применения.

Триггеры автоотката:
- Рост числа записей уровня Error в журналах System и Application более чем вдвое относительно базовой линии
- Появление событий 1000/1001 (Application Error, Windows Error Reporting) для затронутого приложения
- Рост времени загрузки более чем на 20%
- Пользователь вручную запустил то, что Bamboo усыпило или остановило
- Пользователь вручную разморозил процесс

При срабатывании: откат, запись в журнал с причиной, добавление цели в пользовательский белый список, уведомление при следующем возвращении пользователя.

Это ключевой механизм, отсутствующий у аналогов. Он превращает набор твиков в систему, обучающуюся на конкретной машине.

## 13. Протокол IPC

### 13.1 Транспорт

Именованный канал `\\.\pipe\bamboo-{session_id}`, режим сообщений, `PIPE_REJECT_REMOTE_CLIENTS`. Дескриптор безопасности по разделу 3.3.

Кадрирование: `u32` длина в little-endian, затем bincode-сериализованное сообщение. Максимальный размер кадра 4 МБ.

### 13.2 Сообщения

Агент → брокер:

| Сообщение | Назначение |
|---|---|
| `Subscribe { stream, interval }` | Подписка на поток метрик |
| `Unsubscribe { stream }` | Отписка (обязательна при скрытии виджета) |
| `QuerySnapshot { scope }` | Разовый снимок |
| `QueryHistory { app_key, range, resolution }` | Временной ряд |
| `QueryObservations { since }` | Наблюдения анализаторов |
| `Apply { action, target, dry_run }` | Применение действия |
| `Revert { journal_id }` | Откат |
| `RevertAll { since }` | Массовый откат |
| `SetProfile { profile }` | Смена профиля |
| `Whitelist { app_key, scope }` | Добавление в белый список |
| `Investigate { target, duration }` | Сессия расследования ETW |
| `CaptureDump { pid }` | Снятие дампа |
| `ExportReport { range, format }` | Генерация отчёта |

Брокер → агент:

| Сообщение | Назначение |
|---|---|
| `Metrics { ... }` | Поток метрик по подписке |
| `Observation { ... }` | Новое наблюдение |
| `ActionResult { journal_id, status }` | Результат действия |
| `WatchdogFired { journal_id, reason }` | Сработал автооткат |
| `ProfileChanged { profile, reason }` | Смена профиля |
| `Error { code, detail }` | Ошибка |

### 13.3 Требования

Флаг `dry_run` обязателен в `Apply` — на нём строится режим симуляции (раздел 14.6).

Брокер не выполняет ни одну команду без прохождения валидации 3.2. Отказ возвращается с кодом причины, а не молча.

Поток метрик прекращается при отписке или разрыве канала. Брокер не накапливает сообщения для отсутствующего клиента.

## 14. Пользовательский интерфейс

### 14.1 Технология

Slint с фичей `renderer-software`. GPU-контекст не создаётся.

Иконка в трее — крейт `tray-icon`.

Уведомления — Windows Toast через зарегистрированный AppUserModelID в `HKCU\Software\Classes\AppUserModelId\{id}`. Без регистрации Windows молча проглатывает тосты.

### 14.2 Виджет

Компактное окно ~340 × 420, вызывается из трея.

Стили окна (`SetWindowLongPtr` при создании):

| Флаг | Назначение |
|---|---|
| `WS_EX_TOOLWINDOW` | Не показывать в панели задач и Alt+Tab |
| `WS_EX_NOACTIVATE` | Не красть фокус при появлении |
| `WS_EX_TOPMOST` | Переключается кнопкой-булавкой через `SetWindowPos` |
| `WS_EX_LAYERED \| WS_EX_TRANSPARENT` | Опциональный режим сквозных кликов |

Оформление Windows 11: `DwmSetWindowAttribute` с `DWMWA_WINDOW_CORNER_PREFERENCE` = `DWMWCP_ROUND` и `DWMWA_SYSTEMBACKDROP_TYPE` = `DWMSBT_TRANSIENTWINDOW`. Отрисовка выполняется композитором, стоимость нулевая.

**Автоскрытие.** При `SHQueryUserNotificationState` в состоянии `QUNS_RUNNING_D3D_FULL_SCREEN`, `QUNS_BUSY` или `QUNS_PRESENTATION_MODE` виджет скрывается. Проверка — по событию `EVENT_SYSTEM_FOREGROUND`, не поллингом. Без этого оверлей ломает эксклюзивный полноэкранный режим игр.

**Уничтожение при скрытии.** `DestroyWindow`, а не `ShowWindow(SW_HIDE)`, плюс отписка от потока метрик и снижение частоты опроса в брокере. Скрытое живое окно продолжает удерживать ресурсы и получать сообщения.

Содержимое виджета:
- Строка состояния: индикатор активности, собственное потребление CPU, булавка, шестерёнка
- Две карточки: заморожено процессов и освобождено памяти; текущее использование памяти
- Спарклайн памяти за час с отметкой момента вмешательства
- Топ-3 потребителей с бейджами наблюдений («рост 4ч», «простой 2ч»)
- Четыре кнопки: заморозить фоновые, профиль Игра, профиль Батарея, откат

Кнопка отката всегда видима и оформлена деструктивно.

### 14.3 Главное окно

Разделы:

**Обзор** — сводка, активные наблюдения, что Bamboo сделал за период.

**Процессы** — таблица с сортировкой, фильтрами, поиском. Колонки настраиваемые. Двойной клик — детальная карточка с графиками за доступный период, происхождением, действиями.

**Диск** — здоровье накопителей, проекция ресурса, топ по записи, история.

**Загрузка** — график времени загрузки, разбивка по компонентам, корреляция с системным диффом.

**Питание** — пробуждения с причинами, разряд в Modern Standby, удерживающие процессы.

**Автозапуск** — автозагрузка, службы, задачи планировщика в едином списке с влиянием на загрузку.

**Журнал** — все действия, статусы, откат.

**Отчёты** — генерация и экспорт.

**Настройки** — профили, автономность, белые списки, частота уведомлений, бюджеты.

### 14.4 Уведомления

**Определение возможности показа.** Все условия обязательны:
- `SHQueryUserNotificationState` возвращает `QUNS_ACCEPTS_NOTIFICATIONS`
- `SystemPowerRequestList` не содержит `ES_DISPLAY_REQUIRED` (иначе идёт воспроизведение или длительная операция)
- Нет активной передачи данных по сети выше порога
- Нет устойчивой нагрузки CPU без ввода (сборка, рендер — это работа, а не простой)

**Отложенная доставка.** Наблюдения, накопленные за время отсутствия пользователя, доставляются при возвращении. Возвращение определяется событийно: `WTS_SESSION_UNLOCK` через `WTSRegisterSessionNotification` либо переход `GetLastInputInfo` из длительного простоя в активность.

Три обязательных правила:

1. **Схлопывание.** Все накопленные наблюдения — одно уведомление: «за ночь замечено 3 вещи». Разворачивается в виджет. Не серия тостов.
2. **Пауза после возвращения.** 2–3 минуты тишины. Человек сел за компьютер ради своих дел, а не ради советов.
3. **Лимит частоты.** Не чаще одного уведомления в сутки. Убывающая настойчивость: дважды отклонённое предложение по приложению — молчание навсегда, без переспрашивания.

Действия в самом тосте: «Заморозить», «Не трогать», «Подробнее». Реализуются через кнопки тоста и протокол активации.

**Ограничение.** Тосты может показывать только процесс в пользовательской сессии. Служба в сессии 0 этого не может — уведомления отправляет агент по команде брокера.

### 14.5 Отчёт

Еженедельный, одна страница, четыре блока:

1. Расход ресурса SSD: объём за неделю, проекция, разбивка по процессам
2. Фоновые всплески CPU с привязкой к конкретным задачам и службам
3. Тренды роста памяти
4. Что Bamboo сделал за неделю и какой измеримый эффект это дало

Четвёртый блок обязателен — он замыкает петлю обратной связи и не даёт продукту превратиться в набор непроверяемых твиков.

Форматы: HTML для просмотра, Markdown и JSON для экспорта. Markdown-отчёт пользователь может приложить к issue разработчику тормозящего приложения — это превращает Bamboo из «оптимизатора» в диагностический инструмент.

### 14.6 Режим симуляции

«Показать, что было бы сделано, ничего не делая». Реализуется через `dry_run` в `Apply`.

Выводится список предполагаемых действий с обоснованием и ожидаемым эффектом. Пользователь выбирает, что применить.

Это режим по умолчанию для первых 14 дней после окончания периода обучения — он снимает недоверие полностью.

## 15. Безопасность

### 15.1 Модель угроз

| Угроза | Смягчение |
|---|---|
| Локальное повышение привилегий через канал | Дескриптор безопасности, проверка образа клиента, валидация команд |
| Подмена бинарника агента | Проверка подписи или хеша брокером |
| Вредоносное правило из репозитория сообщества | Только через pull request с ревью, версионирование, подпись. Никакой загрузки правил из сети во время работы |
| Отказ в обслуживании через заморозку критичного процесса | Неизменяемый белый список, проверки раздела 11.2 |
| Утечка данных | Отсутствие сетевой активности; данные только локально |
| Повреждение системы при сбое Bamboo | Журнал пишется до действия; разморозка при остановке службы; точки восстановления |

### 15.2 Правила сообщества

Соблазн сделать репозиторий рецептов для конкретных приложений сильный и обоснованный. Но правило — это исполняемое изменение системы, то есть канал поставки атак.

Требования: только через pull request с обязательным ревью двумя мейнтейнерами, версионирование, подпись релиза, поставка вместе с бинарником. Автозагрузка правил из сети во время работы запрещена.

### 15.3 Аудит

`#![forbid(unsafe_code)]` во всех крейтах кроме `bamboo-sys`. `cargo-deny` в CI: проверка лицензий, известных уязвимостей, дубликатов зависимостей. `cargo-audit` при каждой сборке.

## 17. Дистрибуция

### 17.1 Проблема репутации

Профиль поведения Bamboo (служба SYSTEM, манипуляция чужими процессами, ETW-трейсинг, запись в реестр) совпадает с профилем вредоносного ПО. Ожидаемы срабатывания SmartScreen и эвристик антивирусов.

Без сертификата подписи кода SmartScreen показывает «неизвестный издатель» при каждом запуске, Defender может поместить бинарник в карантин.

### 17.2 Меры

- Сборка в GitHub Actions с `attestations: write` — SLSA provenance и воспроизводимость сборки
- Публикация хешей и attestation в релизе
- Раздача через `winget` и `scoop` — репутация набирается на уровне менеджера пакетов
- Подача бинарников на анализ через портал ложных срабатываний Microsoft перед каждым релизом
- Раздел в README с объяснением, почему антивирус может ругаться, и как проверить подлинность сборки
- При появлении средств — сертификат подписи кода (OV достаточно, репутация набирается за месяцы; EV даёт репутацию сразу, но требует HSM)

### 17.3 Установка

MSI или простой инсталлятор, регистрирующий службу с типом `SERVICE_AUTO_START` и флагом отложенного запуска (`SERVICE_DELAYED_AUTO_START`), чтобы не влиять на время загрузки — что было бы иронично.

Портативный режим: работа без установки службы, только наблюдение, все привилегированные функции недоступны. Полезно для диагностики чужих машин.

Удаление: полный откат журнала перед деинсталляцией, обязательно и без возможности пропустить.

## 18. Дорожная карта

Каждый этап самодостаточен и полезен сам по себе.

### 0.1 — Наблюдатель

`bamboo-sys` (снимок процессов, метрики системы), `bamboo-collect`, кольцевые буферы, трей, виджет с топом потребителей.

Ничего не изменяет в системе. Цель этапа — подтвердить соблюдение ресурсного бюджета. Пока это не проверено суточным прогоном, дальше строить рано.

### 0.2 — Знание

SMART и NVMe, анализ пробуждений, регрессии загрузки, Modern Standby, системный дифф.

Ключевой этап для набора аудитории. Эти данные Windows собирает сама и не показывает; конкуренты их не используют. Эффект «оно знает то, чего я не знал» — то, что заставляет людей рассказывать о продукте.

### 0.3 — Расследование

ETW `Kernel-Process`, видеорегистратор, атрибуция задач планировщика, анализ DPC.

Ловит короткоживущие всплески, невидимые для опроса.

### 0.4 — Первые действия

Брокер как служба, журнал, IPC, EcoQoS, приоритет памяти, управление автозагрузкой.

Все действия обратимые, уровни риска 1–2.

### 0.5 — Полный инструментарий

Заморозка со всеми проверками, управление службами, профили, режим симуляции.

### 0.6 — Проактивность

Анализатор простаивающих приложений, отложенные уведомления, еженедельный отчёт, базовая линия.

### 1.0 — Автономность

Автономный режим для уровней 1–2, сторожевой таймер, автооткат, обучение на отклонениях.

Сознательно последний этап: требует, чтобы журнал и сторожевой таймер были обкатаны на живых пользователях. Выпуск автоматики раньше гарантирует issue вида «после обновления пропал интернет».

## 19. Открытые вопросы

- Таблица TBW по моделям накопителей: собирать вручную, парсить открытые базы или запрашивать у пользователя
- Вендор-специфичные атрибуты SMART для SATA: объём работы по составлению таблицы соответствий
- Определение задачи планировщика по родительскому `svchost`: надёжность сопоставления по времени против прямого чтения провайдера TaskScheduler
- Поведение `JobObjectFreezeInformation` для процессов, уже входящих в чужой job object (частый случай для UWP и контейнеров)
- Стратегия для ARM64: доступность части NT API и корректность интерпретации P/E-ядер
- Формат правил сообщества и модель их доверия
- Локализация: минимум русский и английский, механизм перевода строк Slint
